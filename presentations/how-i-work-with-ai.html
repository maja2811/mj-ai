  4. I review the changes against the acceptance criteria and decide what needs another pass.

Example · Shared data quality module

Building the data quality module

We worked through what should happen when checks fail and how projects would use the results.

Explore and decide

What happens when a check fails?

I use AI to explore the existing check framework and agree on the failure behaviour.

We need to check incoming data before writing it, as well as stored tables.

AI implementation

Implement the agreed behaviour

AI implements modes to stop on errors, separate valid rows or quarantine failures.

It saves check results in a shared table and builds a notebook report.

My review

Test the failure paths

I check which failures stop the job and whether flagged rows can continue by mistake.

We check new records where possible rather than scanning the full table.

I review these design decisions before implementation, then check the tests and reports.

Example · CSF raw to cleansed

Unpacking a large semistructured data model

Explore Raw

Complex schemas and relationships

We explore the schemas and source contracts across a large data model.

We work through nested records, keys and how the documents relate.

Design and implement

Plan the table loads

We plan loading in batches with safe restart points.

AI implements the table loads, history and child records.

My review and redesign

Remove unnecessary steps

I found an overengineered loading design and worked through a more direct approach.

My review and input improved loading performance per table by about 75%.

Even with a thorough plan and a newer model, I found design choices we needed to simplify.

We keep Raw unchanged and transform in Cleansed. I use DEV runs to review the changes.
