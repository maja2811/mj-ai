CSF booking data: guide to the cleansed layer

This guide is for analysts and business users who query the CSF booking data. It explains what the data is, how to find your way in Unity Catalog, and how to join the tables correctly. Ready-made SQL is in the example queries.

Not all sales yet

Sales are moving to this system gradually, so the data does not yet contain all of DSB's sales. Keep that in mind before using it for total sales figures.

What the data is

CSF (customer sales flow) holds the bookings made through DSB's new sales system (Sales Component, S3/Sqills), for example in the app, on the web, at ticket machines and at manned sales points.

A booking changes over time: it is created, confirmed, changed or refunded. The tables keep every version of every booking, split into passengers, offers and products, journeys, reservations and seats, admissions, refunds, documents and fulfillment.

4

Current data and history

Every table keeps all versions. Two columns tell you when a version was valid:

_app_valid_from and _app_valid_to

The current version has _app_valid_to = '9999-12-31'.

As it was at a given time t

_app_valid_from <= t AND t < _app_valid_to

Columns such as created_on, valid_from and valid_until are business dates from the sales system. They do not control the history.

5

Joining tables

Pick the moment you want, take the version of each table that was valid at that moment, and join on the ID columns shown under "View relationships", for example booking_id, or booking_id and offer_id. This one rule works for every table:

Rule 1

Current data

Filter every table on

_app_valid_to = '9999-12-31'
Rule 2

At a given time t

Time travel: filter every table on

_app_valid_from <= t AND t < _app_valid_to
Rule 3

Join on IDs

Join on the ID columns shown under "View relationships", for example booking_id, or booking_id and offer_id.

The history of a booking with its details

For each booking version, take the detail version that was valid at that booking version's time:

d._app_valid_from <= b._app_valid_from AND b._app_valid_from < d._app_valid_to

See the last query in the example queries.

"View relationships" also shows _app_valid_from on each link. You do not need to join on it: the time rule above already picks the right version. Joining on an exact _app_valid_from misses rows in book_offer_trip_leg_product_association, which only gets a new version when the association itself changes.

6

Reading amounts

Amounts are stored as whole numbers with a scale and a currency, for example price_amount, price_scale and price_currency. The real amount is:

price_amount / power(10, price_scale) in price_currency
7

Data quality

Every night's update runs two checks.

Check 1

Belongs to a booking

Each row belongs to a booking, for example every passenger has a booking.

Check 2

No duplicates

No row appears twice.

Problems are reported to the BI Commercial team.

8

Known limitations

  • The data starts in March 2026. How long it is kept (6 years) is still an open question with the source team.
  • The actual arrival and departure times on stops are only filled when the sales app sends them.
  • Not every reserved seat links to a trip leg. Use a LEFT JOIN, as in the seats query.
  • If something is removed from a booking later, for example a passenger, it can still show as current. This has not happened in the data so far.

CSF booking data: example queries

Ready-made SQL for commercial_prd.csf_cleansed. Each query was tested against the production data on 2026-11-09. Read the guide above first for the rules on current data, history and joins.

Keep queries fast

Filter every table on current data or a point in time, and limit each query to one booking or a period, as the queries below do. The summary queries take bookings created in October 2026 (the monthly overview: August to October), filtered on b.created_on. Change the dates to the period you need. A query without such a limit reads every booking, and a detail query returns millions of rows.

All queries return current data (_app_valid_to = '9999-12-31') unless they say otherwise.

01

Bookings per month and sales channel

The data does not yet contain all of DSB's sales (see the guide above), so these are totals for the new sales system only.

SQL
SELECT date_trunc('month', created_on) AS month,
       sales_channel,
       count(*) AS bookings,
       sum(confirmed_price_amount / power(10, confirmed_price_scale)) AS confirmed_price
FROM commercial_prd.csf_cleansed.book
WHERE _app_valid_to = '9999-12-31'
  AND created_on >= '2026-08-01' AND created_on < '2026-11-01'
GROUP BY ALL
ORDER BY month DESC, bookings DESC;
02

A booking as it looked at a given time

booking_code is the code the customer sees, so it is handy for looking a booking up. The source can reuse codes over time, so always join tables on booking_id.

SQL
SELECT booking_id, booking_code, sales_channel, fulfillment_type,
       confirmed_price_amount / power(10, confirmed_price_scale) AS confirmed_price
FROM commercial_prd.csf_cleansed.book
WHERE booking_code = 'ABC123'
  AND _app_valid_from <= TIMESTAMP '2026-10-01 12:00:00'
  AND TIMESTAMP '2026-10-01 12:00:00' < _app_valid_to;
03

All versions of one booking

SQL
SELECT _app_valid_from, _app_valid_to, fulfillment_type,
       confirmed_price_amount / power(10, confirmed_price_scale) AS confirmed_price
FROM commercial_prd.csf_cleansed.book
WHERE booking_code = 'ABC123'
ORDER BY _app_valid_from;
04

Passengers by passenger type

SQL
SELECT p.type AS passenger_type,
       count(*) AS passengers,
       count(DISTINCT p.booking_id) AS bookings
FROM commercial_prd.csf_cleansed.book b
JOIN commercial_prd.csf_cleansed.book_passenger p
  ON p.booking_id = b.booking_id
 AND p._app_valid_to = '9999-12-31'
WHERE b._app_valid_to = '9999-12-31'
  AND b.created_on >= '2026-10-01' AND b.created_on < '2026-11-01'
GROUP BY ALL
ORDER BY passengers DESC;
05

Offers and their products

SQL
SELECT o.offer_type,
       pr.code AS product_code,
       pr.travel_class,
       count(*) AS products
FROM commercial_prd.csf_cleansed.book b
JOIN commercial_prd.csf_cleansed.book_offer o
  ON o.booking_id = b.booking_id
 AND o._app_valid_to = '9999-12-31'
JOIN commercial_prd.csf_cleansed.book_offer_product pr
  ON pr.booking_id = o.booking_id
 AND pr.offer_id = o.offer_id
 AND pr._app_valid_to = '9999-12-31'
WHERE b._app_valid_to = '9999-12-31'
  AND b.created_on >= '2026-10-01' AND b.created_on < '2026-11-01'
GROUP BY ALL
ORDER BY products DESC;
06

The journey of a booking: trip legs and stops

SQL
SELECT l.trip_id, l.trip_leg_index, s.trip_stop_index, s.location_name,
       s.planned_departure_time, s.planned_arrival_time
FROM commercial_prd.csf_cleansed.book_trip_leg l
JOIN commercial_prd.csf_cleansed.book_trip_leg_stop s
  ON s.booking_id = l.booking_id
 AND s.trip_id = l.trip_id
 AND s.trip_leg_index = l.trip_leg_index
 AND s._app_valid_to = '9999-12-31'
WHERE l._app_valid_to = '9999-12-31'
  AND l.booking_id = '<booking_id>'
ORDER BY l.trip_id, l.trip_leg_index, s.trip_stop_index;
07

Reserved seats with the passenger and trip leg

passenger_ids is a list, so explode it first. Not every seat links to a trip leg, so that join is a LEFT JOIN. The query shows one booking; all current seats are millions of rows.

SQL
WITH seat AS (
  SELECT booking_id, coach_number, place_numbers,
         trip_leg_coverage_trip_id, trip_leg_coverage_leg_id,
         explode(passenger_ids) AS passenger_ref
  FROM commercial_prd.csf_cleansed.book_reserved_place
  WHERE _app_valid_to = '9999-12-31'
    AND booking_id = '<booking_id>'
)
SELECT seat.booking_id, seat.coach_number, seat.place_numbers,
       p.type AS passenger_type, l.trip_leg_index
FROM seat
JOIN commercial_prd.csf_cleansed.book_passenger p
  ON p.booking_id = seat.booking_id
 AND p.external_ref = seat.passenger_ref
 AND p._app_valid_to = '9999-12-31'
LEFT JOIN commercial_prd.csf_cleansed.book_trip_leg l
  ON l.booking_id = seat.booking_id
 AND l.trip_id = seat.trip_leg_coverage_trip_id
 AND l.trip_leg_index = cast(seat.trip_leg_coverage_leg_id AS INT)
 AND l._app_valid_to = '9999-12-31';
08

Refund offers by status

SQL
SELECT r.status,
       count(*) AS refund_offers,
       sum(r.refundable_amount_amount / power(10, r.refundable_amount_scale)) AS refundable,
       sum(r.refund_fee_amount / power(10, r.refund_fee_scale)) AS fees
FROM commercial_prd.csf_cleansed.book b
JOIN commercial_prd.csf_cleansed.book_refund_offer r
  ON r.booking_id = b.booking_id
 AND r._app_valid_to = '9999-12-31'
WHERE b._app_valid_to = '9999-12-31'
  AND b.created_on >= '2026-10-01' AND b.created_on < '2026-11-01'
GROUP BY ALL
ORDER BY refund_offers DESC;
09

Products per trip leg (associations)

The association lists every product considered for a trip leg, with a status. Only booked products match book_offer_product, so that join is a LEFT JOIN. It is the largest table, so expect about a minute for one month.

SQL
SELECT a.product_code, a.status_code, pr.travel_class, l.trip_leg_index,
       count(*) AS associations
FROM commercial_prd.csf_cleansed.book b
JOIN commercial_prd.csf_cleansed.book_offer_trip_leg_product_association a
  ON a.booking_id = b.booking_id
 AND a._app_valid_to = '9999-12-31'
JOIN commercial_prd.csf_cleansed.book_offer o
  ON o.booking_id = a.booking_id
 AND o.offer_id = a.offer_id
 AND o._app_valid_to = '9999-12-31'
LEFT JOIN commercial_prd.csf_cleansed.book_offer_product pr
  ON pr.booking_id = a.booking_id
 AND pr.offer_id = a.offer_id
 AND pr.code = a.product_code
 AND pr._app_valid_to = '9999-12-31'
LEFT JOIN commercial_prd.csf_cleansed.book_trip_leg l
  ON l.booking_id = a.booking_id
 AND l.trip_id = o.trip_coverage_covered_trip_id
 AND l.trip_leg_index = a.trip_leg_index
 AND l._app_valid_to = '9999-12-31'
WHERE b._app_valid_to = '9999-12-31'
  AND b.created_on >= '2026-10-01' AND b.created_on < '2026-11-01'
GROUP BY ALL
ORDER BY associations DESC;
10

Passengers per passenger type on admissions

One passenger can hold several types on one admission, so count distinct passenger_ref.

SQL
SELECT t.passenger_type,
       count(DISTINCT t.booking_id, t.passenger_ref) AS passengers
FROM commercial_prd.csf_cleansed.book b
JOIN commercial_prd.csf_cleansed.book_admission a
  ON a.booking_id = b.booking_id
 AND a._app_valid_to = '9999-12-31'
JOIN commercial_prd.csf_cleansed.book_admission_passenger_type t
  ON t.booking_id = a.booking_id
 AND t.offer_id = a.offer_id
 AND t.admission_id = a.admission_id
 AND t._app_valid_to = '9999-12-31'
WHERE b._app_valid_to = '9999-12-31'
  AND b.created_on >= '2026-10-01' AND b.created_on < '2026-11-01'
GROUP BY ALL
ORDER BY passengers DESC;
11

A booking's history with its detail rows (time travel)

For each booking version, take the passenger version that was valid at that time. The same rule works for every table.

SQL
SELECT b._app_valid_from, b.fulfillment_type, p.passenger_id, p.type AS passenger_type
FROM commercial_prd.csf_cleansed.book b
JOIN commercial_prd.csf_cleansed.book_passenger p
  ON p.booking_id = b.booking_id
 AND p._app_valid_from <= b._app_valid_from
 AND b._app_valid_from < p._app_valid_to
WHERE b.booking_code = 'ABC123'
ORDER BY b._app_valid_from, p.passenger_id;
